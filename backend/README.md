# FixCampus Backend — Python + FastAPI + SQLite

Centralised Campus Problem Reporting Platform. Implements the three modules
from the project brief:

1. **Issue Reporting** — validated ticket creation with a unique ticket code
2. **Categorisation & Routing** — keyword-based priority scoring, duplicate
   detection at the same location, automatic routing to one of 5 departments
3. **Tracking, Notification & Resolution** — status flow, SLA breach
   detection, reporter confirmation / reopen, feedback

Every API response is JSON (FastAPI + Pydantic handle this automatically).
The database is a single SQL (SQLite) file — plain SQL via Python's built-in
`sqlite3` module, no ORM, so the schema and every query are easy to read and
modify directly.

## Requirements

- Python 3.10+
- `pip`

## Setup

**Fastest option:** run `setup.ps1` (Windows PowerShell) or `setup.sh`
(macOS/Linux) from inside this folder — it does everything below in one
step and then starts the server.

```powershell
# Windows (PowerShell)
.\setup.ps1
```
```bash
# macOS / Linux
bash setup.sh
```

**Manual setup**, one command at a time — pick the block for your shell,
don't mix them (`&&` and `source` are bash-only and will error in
PowerShell):

Windows (PowerShell):
```powershell
cd backend
python -m venv venv
venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
uvicorn app.main:app --reload --port 8000
```
If activation is blocked by a red "execution policy" error, run this once
and try again:
```powershell
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
```

macOS / Linux:
```bash
cd backend
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
uvicorn app.main:app --reload --port 8000
```

Either way, edit `JWT_SECRET` in `.env` before deploying anywhere real.

The server creates `database/fixcampus.db` automatically on first run and
seeds exactly **two admin accounts** and the **5 departments** — nothing
else. No dummy students, staff, tickets, or reviews.

Interactive API docs (auto-generated by FastAPI) are at
`http://localhost:8000/docs` once it's running.

## The 5 departments

| Category | Department | Default priority |
|---|---|---|
| `classroom` | Classroom Support | Medium |
| `lab` | Lab Support | High |
| `network` | IT / Network Department | Medium |
| `cleanliness` | Housekeeping | Low |
| `facility` | Facility & Civil Admin | High |

A ticket's `category` determines its department automatically. Priority can
be escalated to High if the description contains an urgency keyword (see
`app/utils.py` — `no water`, `wifi down`, `exposed wire`, `fire`, `gas leak`,
`flooding`, `no power`, etc.), but is never downgraded.

## Accounts

| Role | Email | Password |
|---|---|---|
| Admin | `admin1@fixcampus.edu` | `admin123` |
| Admin | `admin2@fixcampus.edu` | `admin123` |

These are the **only** admin accounts — there is no admin self-registration
route. Change these passwords directly in the database before any real
deployment. Students register and can log in immediately; staff register
against a department and stay `pending` until an admin approves them.

## API reference

All authenticated routes take `Authorization: Bearer <token>`.

### Auth
| Method | Route | Notes |
|---|---|---|
| POST | `/api/auth/register` | `{name, email, password, role, department_id?}` — student is active immediately, staff is `pending` |
| POST | `/api/auth/login` | `{email, password, role?}` |

### Departments
| Method | Route |
|---|---|
| GET | `/api/departments` |

### Tickets
| Method | Route | Who | Notes |
|---|---|---|---|
| POST | `/api/tickets` | any authenticated user | JSON: `{title?, category, location, description}` |
| POST | `/api/tickets/{id}/photo` | reporter or admin | multipart file upload, optional |
| GET | `/api/tickets` | any authenticated user | students see their own; staff see their department (or `?scope=assigned`); admin sees all, filterable by `status`, `category`, `priority` |
| GET | `/api/tickets/{id}` | owner / same-department staff / admin | includes full status history |
| PATCH | `/api/tickets/{id}/status` | staff (own dept) / admin | `{status, note?}` — `status` ∈ `acknowledged, in_progress, resolved` |
| PATCH | `/api/tickets/{id}/assign` | admin | `{assigned_to}` — must be active staff in the ticket's department |
| POST | `/api/tickets/{id}/confirm` | the reporter | `{confirmed, rating?, comment?}` — closes the ticket or reopens it |

### Users (admin only)
| Method | Route |
|---|---|
| GET | `/api/users?role=&status=&department_id=` |
| PATCH | `/api/users/{id}/approve` |
| PATCH | `/api/users/{id}/reject` |

### Feedback & stats
| Method | Route | Who |
|---|---|---|
| GET | `/api/feedback` | public |
| GET | `/api/stats/overview` | public — `{resolved, users, avgResponseTime}` |
| GET | `/api/stats/departments` | admin |
| GET | `/api/stats/hotspots` | admin — repeat-ticket locations |
| GET | `/api/stats/sla-breaches` | admin |

## Status flow

```
reported → acknowledged → in_progress → resolved → closed
                                            ↓
                                    (reporter says "not fixed")
                                            ↓
                                      in_progress (reopened)
```

Only the reporter can move a ticket from `resolved` to `closed` (or reopen
it) — that's `POST /api/tickets/{id}/confirm`.
